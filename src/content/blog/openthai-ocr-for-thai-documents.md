เอกสารหลายชุดที่อยากนำมาใช้กับ AI ยังเป็นรูปภาพหรือ PDF สแกน เปิดอ่านเองได้ แต่ค้นคำหรือคัดลอกข้อความไปใช้ต่อไม่สะดวก ถ้าจะเริ่มแก้ปัญหานี้ ผมอยากเริ่มจากการอ่านเอกสารให้เป็นข้อความที่ตรวจย้อนกลับได้ ก่อนคิดถึงแชตบอตที่ตอบได้ทุกเรื่อง

OpenThai 2.0 OCR เป็นตัวเลือกหนึ่งที่น่าลอง ผู้พัฒนาแยกโมเดลสำหรับอ่านข้อความออกจากโมเดลที่เก็บโครงสร้างหน้าเอกสาร ซึ่งช่วยให้เลือกตามงานได้ ไม่จำเป็นต้องใช้ตัวที่หนักที่สุดกับทุกหน้า[1][2]

บทความนี้รวมแนวทางจากเอกสารผู้พัฒนา กับ **ผลทดสอบ OCR Text บน CPU เครื่องของผมด้วยภาพที่สร้างเอง** ส่วน OCR Markdown และ Safari ยังไม่ได้ทดสอบ ตัวอย่างการเชื่อมระบบด้านล่างยังเป็นข้อเสนอ ไม่ใช่ระบบที่เปิดใช้งานแล้ว

## เลือกก่อนว่าอยากได้ข้อความ หรือต้องรักษาตาราง

ถ้าต้องการข้อความจากหนังสือ ประกาศ หรือเอกสารพิมพ์ไทยและอังกฤษเพื่อค้นคำ ให้เริ่มพิจารณา **OpenThai2.0-OCR-Text** รุ่นนี้รันบน CPU ไม่ต้องใช้ GPU และคืนข้อความตามลำดับการอ่าน พร้อมกรอบและค่าความมั่นใจรายบรรทัด แต่ไม่ได้คืนโครงสร้างตารางเป็น Markdown[1]

ถ้าข้อมูลสำคัญอยู่ในตาราง เช่น ตัวเลขที่ต้องอยู่คู่กับหัวคอลัมน์ ให้พิจารณา **OpenThai2.0-OCR-Markdown** ซึ่งคืน Markdown และใช้ HTML สำหรับตาราง รวมถึงเซลล์ที่คร่อมแถวหรือคอลัมน์ รุ่นนี้เป็นคนละโมเดลกับ Text ไม่ใช่การเปิดตัวเลือก export เพิ่ม[2][4]

ในงานของผม ผมจะเริ่มด้วย Text สำหรับการค้นเอกสาร แล้วแยกหน้าที่ต้องรักษาตารางไปทดลอง Markdown อีกชุดหนึ่ง วิธีนี้ยังเป็นแผนทดลอง ไม่ใช่ข้อสรุปว่าจะเร็วหรือแม่นกว่าบนเอกสารทุกชนิด

## คำว่า 4 MB ต้องอ่านให้ครบ

ขนาดประมาณ 4 MB ที่พูดถึงกันคือน้ำหนักโมเดลของรุ่น Text ประกอบด้วยตัวตรวจหาข้อความและตัวอ่านข้อความ ไม่ใช่ขนาดโปรแกรมพร้อม dependency หรือ RAM ที่ใช้ทั้งหมด ส่วนรุ่น Markdown มีขนาดดาวน์โหลดใหญ่กว่ามาก ผู้พัฒนาระบุประมาณ 2.5 GB ในคู่มือติดตั้ง[1][4]

เรื่องนี้มีผลกับการออกแบบระบบ ถ้าจะให้คนเปิดเว็บแล้วเลือกภาพอ่านทันที ผมต้องสนใจทั้งขนาดที่ดาวน์โหลดครั้งแรกและเวลาที่เครื่องพร้อมใช้งาน ไม่ใช่ดูเฉพาะขนาดไฟล์โมเดล

ตัวเลขในคู่มือเป็นผลที่ผู้พัฒนาวัดบนฮาร์ดแวร์และเอกสารของเขา[4] ส่วนตัวเลขในหัวข้อผลทดสอบด้านล่างวัดบนเครื่องของผม แยกกันคนละชุด ไม่ควรใช้แทนกันหรือเป็นคำสัญญาความเร็วของระบบจริง

## ทางที่เริ่มง่าย: ทดลองจาก browser ด้วยภาพที่ไม่เป็นความลับ

Thai Pangsakulyanont ทำเดโม OpenThai OCR บน browser โดยใช้ ONNX Runtime Web หน้าเดโมรับรูปภาพและแสดงข้อความที่อ่านได้ ผู้ทำเดโมระบุว่าประมวลผลบนอุปกรณ์ และดาวน์โหลดโมเดลรวม runtime ประมาณ 20 MB[3]

ถ้าจะเริ่มทดลอง ผมจะใช้ภาพประกาศที่เผยแพร่สาธารณะ เปิดเดโม เลือกภาพ แล้วเทียบข้อความกับภาพทีละบรรทัด โดยเฉพาะชื่อคน ตัวเลข วันที่ และคำปฏิเสธ จากนั้นค่อยลองภาพที่ถ่ายเอียงหรือแสงไม่ดี เพื่อดูว่าพลาดตรงไหน

เดโมนี้ไม่ได้ยกความสามารถของ Python runtime มาทั้งหมด โค้ดระบุว่ายังข้ามการแก้ทิศทาง การปรับความเอียง และการแยกช่องว่างบางส่วน จึงไม่ควรนำผลของเดโมไปสรุปแทนรุ่น Python หรือกลับกัน[3]

สำหรับ iPhone ผมสนใจทางนี้เพราะอยากถ่ายเอกสารแล้วคัดลอกข้อความไปใช้ต่อ แต่ยังต้องทดสอบบน Safari จริงก่อน จึงยังบอกไม่ได้ว่าภาพใหญ่จะกินหน่วยความจำเท่าไร โหลดครั้งแรกนานแค่ไหน หรือใช้งานต่อหลังตัดอินเทอร์เน็ตได้ครบหรือไม่

แม้เดโมระบุว่าทำ OCR บนอุปกรณ์ ก็ยังมีการโหลดโค้ดและโมเดลจากภายนอกในครั้งแรก[3] ก่อนใช้กับเอกสารภายใน ผมจะตรวจ network requests และนโยบายของเว็บทั้งหน้าอีกครั้ง ไม่ใช้คำว่า on-device เป็นหลักฐานรับรองว่าเว็บทุกส่วนไม่มีการรับส่งข้อมูล

## ถ้าจะทำงานเป็นชุด ให้เริ่มจากคู่มือ Python

คู่มือทางการมีขั้นตอนสำหรับ Windows, macOS และ Linux แยกการติดตั้ง OCR Text กับ OCR Markdown รวมถึงสคริปต์อ่านรูปภาพและ PDF เป็นไฟล์ข้อความหรือ Markdown[4]

การทดลองรอบนี้ใช้สภาพแวดล้อม Python แยกจากโปรเจกต์หลัก และเอกสารสมมติที่ไม่มีข้อมูลจริง ยังไม่ต่อเข้าระบบ production

ลำดับที่อยากทำคือ:

1. เลือกเอกสารตัวอย่างที่หน้าตาใกล้กับงานจริง ไม่เลือกเฉพาะหน้าที่อ่านง่าย
2. เตรียมข้อความอ้างอิงที่คนตรวจแล้วไว้เทียบผล
3. ทำตามคู่มือทางการ เก็บรุ่นโมเดลและ dependency ที่ใช้
4. บันทึกผลแยกรายหน้า พร้อมเวลาที่ใช้และข้อผิดพลาด
5. ดูหน้าที่อ่านผิดก่อนตัดสินใจว่าจะนำไปใช้กับงานใด

สคริปต์ทดลอง รุ่น dependency ภาพที่ป้อน ข้อความอ้างอิง และผลดิบอยู่ในชุดหลักฐานที่แนบด้านล่าง ส่วนคู่มือติดตั้งฉบับเต็มของผู้พัฒนาอยู่ท้ายบทความ

## ผลทดสอบจริงบนเครื่อง: ข้อความอ่านได้ แต่ตัวเลขในตารางหาย

ทดลองวันที่ 15 พฤศจิกายน 2026 บน **Apple M5 Max, RAM 128 GiB** ใช้ Python 3.13.18, ONNX Runtime 1.32.0, `CPUExecutionProvider` และ 2 threads ไม่ใช้ GPU สำหรับ OCR

ปัก revision ของโมเดลเป็น `40e8e9ff752b65153b1a71d521ec9390882afd7e` ทดสอบด้วยฟอนต์ Sarabun ขนาด 16 pt บนหน้ากระดาษ A4 ที่สร้างเอง แปลงเป็นภาพ 200 DPI ก่อนป้อนเข้า OCR โมเดลเห็นเฉพาะพิกเซล PNG ไม่ได้อ่านข้อความจาก text layer ของ PDF

มีเอกสารต้นแบบ 3 หน้า เพิ่มภาพประกาศหมุน 7 องศา ภาพประกาศลดขนาดพร้อม Gaussian blur และหน้าว่าง รวม 6 เคส ภาพเอียงกับภาพเบลอใช้ข้อความเดียวกับประกาศ จึงไม่ใช่เอกสารอิสระเพิ่มอีกสองฉบับ หน้าปกติมีขนาด 1653 × 2339 พิกเซล ภาพเบลอมีขนาด 827 × 1169 พิกเซล ใช้ Gaussian blur radius 0.8

วอร์มโมเดลด้วยหน้าประกาศ 1 ครั้ง จากนั้นวัดแต่ละเคส 3 ครั้ง ตารางแสดงค่ากลางของเวลา `LineOCR.read()` ซึ่งรวมการอ่านไฟล์ภาพ แต่ไม่รวมดาวน์โหลด โหลดโมเดล สร้างภาพ หรือแปลง PDF เวลาโหลดโมเดลครั้งนี้ประมาณ 0.457 วินาที จึงไม่ควรอ่านเวลาต่อภาพว่าเป็นเวลารอตั้งแต่เปิดแอป

| ภาพที่ทดสอบ | ค่ากลาง วินาที/ภาพ | CER หลังตัด whitespace |
| --- | ---: | ---: |
| ประกาศภาษาไทย | 0.131 | 0.35% |
| ใบแจ้งยอดไทยผสมอังกฤษ | 0.140 | 0.42% |
| ตารางรายการสินค้า | 0.124 | 4.65% |
| ประกาศเดิม หมุน 7 องศา | 0.223 | 0.00% |
| ประกาศเดิม ลดขนาดและเบลอ | 0.112 | 0.00% |
| หน้าว่าง | 0.074 | ไม่คำนวณ (ไม่มีข้อความอ้างอิง) |

CER คืออัตราความผิดพลาดระดับตัวอักษร ยิ่งต่ำยิ่งดี รอบนี้ปรับ Unicode เป็น NFC และตัด whitespace ทั้งหมดก่อนเทียบ โดยยังแยกตัวพิมพ์ใหญ่กับเล็ก นับ Unicode code points ไม่ใช่อักขระไทยที่รวมวรรณยุกต์เป็นหนึ่งกลุ่ม วิธีนี้จึงไม่ได้วัดความถูกต้องของช่องว่าง การขึ้นบรรทัด หรือรูปแบบตาราง

สิ่งที่ผิดจริงมีดังนี้:

- หน้าประกาศทำจุดหลัง `น.` หายหนึ่งตำแหน่ง
- ใบแจ้งยอดอ่าน `Invoice` เป็น `InVoice` แต่เลข `125.50`, `1,506.00`, `1,456.00`, รหัส `INV-2026-001` และข้อความ `ยังไม่ได้ชำระเงิน` ตรงกับตัวอย่าง
- ตารางทำเลขจำนวน **2, 3, 1 และ 6 หายจากข้อความผลลัพธ์** แม้ชื่อสินค้าและราคายังอยู่ ผมตรวจภาพต้นทางแล้ว เลขทั้งสี่มีอยู่จริงในคอลัมน์จำนวน
- หน้าว่างคืนข้อความว่าง ไม่สร้างข้อความขึ้นมาในเคสนี้

ตัวอย่างตารางบรรทัดแรก:

```text
ต้นฉบับ: กาแฟ 2 120.00
ผล OCR:  กาแฟ 120.00
```

ข้อผิดพลาดนี้ทำให้เห็นว่าตารางใช้ต่อเป็นรายการซื้อขายไม่ได้ แม้ CER อยู่เพียง 4.65% ในภาพตัวอย่างนี้ การอ่านราคาถูกแต่จำนวนหายยังเป็นความผิดพลาดของงาน ไม่ใช่ผลที่ควรยอมรับแล้วให้ AI เดาต่อ

ภาพประกาศที่หมุนและภาพที่เบลอได้ CER 0% ในรอบนี้ แต่ไม่ได้แปลว่าการหมุนหรือเบลอช่วยให้ OCR แม่นขึ้น ใช้ภาพต้นแบบเพียงหน้าเดียว และการสร้างภาพใหม่เปลี่ยนรูปร่างพิกเซลด้วย ผลข้อความของแต่ละเคสเหมือนกันทั้ง 3 รอบ แต่ยังไม่ใช่หลักฐานความเสถียรบนเอกสารหลากหลาย

**ผลนี้เป็น smoke test ขนาดเล็กบนเอกสารสังเคราะห์ ไม่ใช่ benchmark ความแม่นยำบนเอกสารจริง** หน้าทดสอบค่อนข้างโล่ง ยังไม่มีภาพถ่ายจากโทรศัพท์ เอกสารสแกนเก่า ลายมือ ตารางซับซ้อน หรือการเทียบกับ OCR ตัวอื่น ยังไม่ได้วัด RAM สูงสุด เวลาตรวจแก้โดยคน หรือผลบน OCR Markdown และ Safari

[ดาวน์โหลดภาพ ข้อความอ้างอิง สคริปต์ รุ่นแพ็กเกจ และ results.json](../../downloads/openthai-ocr-smoke-20261115.zip) เพื่อดูผลดิบและทำซ้ำได้ โดยสคริปต์สร้างภาพใหม่ต้องมี Chrome กับฟอนต์ Sarabun ตาม path ที่ระบุไว้ หรือใช้ PNG ที่แนบมาเพื่อทดสอบ inference ซ้ำโดยไม่สร้างภาพใหม่

## จาก OCR ไปสู่คลังความรู้ที่ค้นย้อนกลับได้

งานแรกที่ผมอยากนำไปใช้คือช่วยอ่านเอกสารแนบก่อนเข้าคลังความรู้ ทางเดินที่เสนอคือ:

```text
เอกสารต้นฉบับ
  → ตรวจว่ามีข้อความที่ดึงออกมาได้อยู่แล้วหรือไม่
  → ถ้าจำเป็นจึงทำ OCR แยกรายหน้า
  → เก็บข้อความพร้อมชื่อไฟล์และเลขหน้า
  → ตรวจคำสำคัญและหน้าที่อ่านไม่สำเร็จ
  → แบ่งข้อความเพื่อทำดัชนีค้นหา
  → ให้ AI ตอบพร้อมชี้กลับไปยังหน้าต้นฉบับ
```

ผมจะเก็บต้นฉบับไว้เสมอ ผล OCR เป็นข้อมูลอีกชั้นหนึ่ง ไม่เขียนทับเอกสารเดิม และจะบันทึกด้วยว่าใช้โมเดลรุ่นใดประมวลผล เพื่อให้ย้อนทำใหม่หรือเปรียบเทียบผลได้

ตัวอย่างเช่น ระบบช่วยค้นเอกสารประชุมอาจตอบว่าเจอประเด็นหนึ่งในไฟล์ใด หน้าใด แล้วเปิดหน้านั้นให้คนตรวจ ไม่ใช่นำข้อความที่อ่านได้ไปสรุปทันทีโดยไม่มีทางกลับไปดูภาพ

ถ้าเป็นงานหลังบ้านร้านกาแฟ ผมจะเริ่มจากช่วยคัดลอกข้อความให้คนตรวจ ไม่ให้ผล OCR สร้างรายการบัญชีหรือยืนยันยอดเอง ส่วนการอ่านตารางรายการสินค้า ผมจะแยกทดสอบว่าแต่ละจำนวนจับคู่กับรายการถูกต้องหรือไม่ ไม่ดูแค่ว่าตัวหนังสือออกมาครบ

ทั้งหมดนี้เป็นรูปแบบการเชื่อมระบบที่เสนอในบทความ ยังไม่ใช่ความสามารถที่เปิดใช้แล้วใน MeetFlow, POS หรือคลังความรู้ของผม

## วัดความถูกต้องที่งานต้องใช้

ผมอยากรู้ว่า OCR ช่วยลดเวลาตรวจเอกสารได้จริงแค่ไหน มากกว่าดูเฉพาะจำนวนหน้าต่อนาที

แบบประเมินชุดแรกควรตอบคำถามเหล่านี้ได้:

- ชื่อบุคคลและชื่อหน่วยงานตรงกับต้นฉบับหรือไม่
- จำนวนเงิน จุดทศนิยม วันที่ และเลขอ้างอิงถูกหรือไม่
- อ่านครบทุกหน้าหรือมีหน้าที่ว่าง หลุด หรือถูกตัด
- ข้อความสองคอลัมน์ยังเรียงลำดับถูกหรือไม่
- ถ้าเป็นตาราง ตัวเลขยังผูกกับแถวและคอลัมน์เดิมหรือไม่
- คนต้องแก้ผลลัพธ์นานเท่าไร ก่อนนำไปใช้ต่อได้

ค่าความมั่นใจรายบรรทัดที่รุ่น Text คืนมามีประโยชน์สำหรับทำหน้าจอตรวจทาน[1] แต่ผมจะไม่ใช้ค่าสูงเป็นเหตุให้ข้ามการตรวจยอดเงินหรือชื่อคน คำสำคัญผิดเพียงจุดเดียวก็อาจทำให้งานนั้นใช้ต่อไม่ได้ แม้ข้อความส่วนอื่นจะถูก

ลายมือก็ต้องแยกเป็นอีกโจทย์หนึ่ง การ์ดรุ่น Text ระบุว่าเน้นตัวพิมพ์ และยังอ่อนกับลายมือและข้อความในฉากทั่วไป[1] ผมจึงจะไม่เริ่มด้วยการใช้มันอ่านแบบฟอร์มเขียนมือทั้งหมดแล้วคาดหวังผลเหมือนเอกสารพิมพ์

## ก่อนนำไปใช้กับเอกสารจริง

รุ่น Text ใช้ Apache-2.0 ส่วน Markdown ใช้ OpenMDW-1.1 ต้องอ่านเงื่อนไขของแต่ละรุ่น ไม่เหมารวมว่า OpenThai ทุกตัวใช้สัญญาอนุญาตเดียวกัน[1][2]

ด้านข้อมูล ผมจะกำหนดตั้งแต่ต้นว่าใครเปิดต้นฉบับได้ ผล OCR เก็บที่ไหน และ log อนุญาตให้มีข้อความส่วนใดบ้าง ช่วงทดลองไม่ควรใช้ข้อมูลภายในเพียงเพราะติดตั้งโมเดลลงเครื่องได้แล้ว

ถ้าจะเลือกงานเริ่มต้นตอนนี้ ผมเลือก **อ่านเอกสารพิมพ์เพื่อค้นคำ พร้อมเปิดกลับไปดูหน้าต้นฉบับได้** ขอบเขตนี้ช่วยให้ตรวจได้ว่าอ่านครบหรือไม่ และค้นเจอสิ่งที่ต้องการหรือยัง

เมื่อมีผลจากเอกสารจริงแล้ว ค่อยตัดสินใจเรื่องตาราง การทำงานเป็นชุด และการให้ AI ตอบคำถามต่อจากข้อความที่อ่านได้ ผมยังไม่ถือว่าขั้นตอนเหล่านั้นผ่าน เพียงเพราะมีโมเดลพร้อมดาวน์โหลด
